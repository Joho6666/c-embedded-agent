## 4. CI Blocker (P0)

* **故障现象**:
  `backend/tests/test_llm_options.py` 中 2 个带有 `@pytest.mark.asyncio` 的测试在 CI 中报错：
  `Failed: async def functions are not natively supported. You need to install a suitable plugin...`
* **根因**:
  `backend/requirements.txt` 中仅列出 `pytest>=8.3.0`，未包含 `pytest-asyncio`；CI 运行 `pip install -r backend/requirements.txt` 后 pytest 缺乏 async plugin。
* **解决方案**:
  1. 在 `backend/requirements.txt` 中增加 `pytest-asyncio>=0.24.0`。
  2. 在 `backend/pytest.ini` 中显式配置 `asyncio_mode = auto`。
  3. 严禁删除测试、严禁 skip 测试、严禁弱化断言。

## 5. Benchmark Blocker & 对比评测框架设计

* **问题**: 现有 50 个 benchmark tasks 仅是静态 JSON，无规范的 Agent vs Plain LLM 对比执行框架与可复现元数据。
* **方案**:
  1. **公平隔离 (Fairness Isolation)**:
     * 输入完全对齐：同一需求、同一 MCU、同一板型、同一初始工程、同一温度与生成限制。
     * **Plain LLM Baseline**: 零工具调用、直接写代码，禁止使用 Error Memory、知识库、Skill、编译器反馈和自动修复。
     * **C-Embedded Agent**: 使用完整 Agent 能力（Skill、Context Router、GCC 诊断反馈、Error Memory、最多 3 轮自动修复）。
  2. **可复现环境元数据 (`environment.json`)**:
     * Git Commit SHA, OS, Python, Node, ARM GCC 版本, ESP-IDF 状态, Model 名称, Base URL Host（**严禁泄露 API Key**）, temperature, top_p, max_tokens, task hash, project hash。
  3. **输出结构**:
     * 保存至 `benchmark-results/run-YYYYMMDD-HHMM/` (`config.json`, `environment.json`, `baseline.json`, `agent.json`, `summary.json`, `failures/`)。
  4. **无凭据时的严格诚实**:
     * 若未检测到 `LLM_API_KEY`，输出 `{"status": "SKIPPED", "reason": "LLM not configured"}`，各项比率置为 `null`，严禁伪造数字。

## 6. STM32 Blocker & 硬件闭环加固

* **受控迭代闭环**:
  ```text
  Generate/Patch → Build → Static Validate → Flash → Reset → Serial Capture → Marker Check → PASS
                                                                                   ↓ FAIL
                                                  [Auto Fix Loop: max_iterations=3]
  ```
* **硬件测试用例严格判决**:
  * **LED**: 烧录成功但无外部探针确认物理闪烁时，状态判定为 `PARTIAL`，不能判 `PASS`。
  * **USART**: 捕获 `CEA:STM32:PASS` 串口 marker，方可判定为 `VERIFIED_HARDWARE`。
  * **ADC**: 串口输出符合合理数值范围 (0~4095) 判定为 `PASS`。
  * **EXTI**: 需物理按键输入时，明确返回 `MANUAL_STEP_REQUIRED`，严禁假通过。
* **硬件留痕制品 (Hardware Evidence Artifact)**:
  * 每次硬件运行落盘到 `runs/<run-id>/`:
    * `metadata.json`: platform, mcu, board, adapter, firmware artifact, sha256, toolchain, device, timestamp, git_sha (不含密钥)。
    * `build.log`, `flash.log`, `serial.log`, `validation.json`。

## 9. 架构与工具正规化

1. **集中式审批策略 (`ApprovalPolicy`)**:
   * `SAFE`: `read_file`, `list_files`, `retrieve_knowledge`, `static_validate`, `compile_project`
   * `WRITE`: `apply_patch`, `write_file`, `create_project`
   * `HARDWARE`: `flash_firmware`, `reset_device`, `sample_serial`
   * `DANGEROUS`: `erase_flash`, `mass_erase`, `burn_efuse`, `option_bytes` (预留策略，禁止任何自动执行)
2. **结构化 Agent Planner**:
   * 输出结构化 Action Plan：
     `{"goal": str, "platform": str, "steps": [{"tool": str, "reason": str, "expected_evidence": str}], "risk": str, "requires_approval": bool}`
3. **结构化 Error Memory**:
   * 包含 `platform`, `framework`, `error_signature`, `root_cause`, `fix`, `files`, `confidence`, `verified_count`, `last_verified`。
   * 只有在 auto-fix 闭环并再次编译成功的场景下，才递增 `verified_count`。
4. **Context Router 事实溯源**:
   * 增加 `evidence_source`，跟踪 facts 来源于 `project.json`, `sdkconfig`, `Makefile`, `.ioc`, `board profile` 还是 `defaults`。

## 13. 风险与应对

| 风险点 | 应对措施 |
|---|---|
| 本地缺少 Linux Docker 无法本地执行 ESP-IDF smoke | 本地通过适配器接口与单元测试验证逻辑，CI 真实运行 Docker ESP-IDF 6.1 smoke，无本地假执行 |
| 本地无 ST-Link 导致硬件测试失败 | 硬件门禁标定为 `NOT_TESTED`，遵循 NO FAKE PASS，不把缺硬件转为 fake PASS |
| Windows 与 Linux 路径/换行符差异 | 全面使用 `pathlib.Path`，文本统一 `encoding="utf-8"` 与 `errors="replace"` |
| 改动破坏既有 11/11 STM32 Golden 编译 | 每次变更后以 `scripts/golden_build.py` 作为底线回归门禁 |
