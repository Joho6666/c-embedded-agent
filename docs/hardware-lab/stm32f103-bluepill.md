# Hardware Lab — STM32F103 Blue Pill fixture

Reproduce the v0.10 hardware validation loop with this exact fixture.
Every claim below matches `boards/bluepill_f103c8.yaml` and the golden
projects — no guessing for the agent, none for you.

## Bill of materials

| Item | Detail |
|---|---|
| Board | STM32F103 Blue Pill (STM32F103C8T6, LQFP48) |
| Debug probe | ST-Link V2 clone (SWD) |
| USB-UART | CH340 / CP210x adapter (the "USB TO SERIAL" header on-board also works) |
| LED | On-board PC13 (active-low) — external LED on PA5 recommended for GPIO-evidence tests |
| Button | Any tactile switch to GND on PB0 (input mode, internal pull-up) |
| I2C device | 24C02 EEPROM or SSD1306 on I2C1 (PB6=SCL, PB7=SDA), 4.7k pull-ups to 3.3V |
| SPI device | Loopback wire SPI1: PA5=SCK ↔ PA6=MISO (loopback) or an SD/W25Q module |
| ADC source | Potentiometer 0–3.3V on PA1 (ADC1_IN1) |

## Wiring

### ST-Link (SWD)

| ST-Link | Blue Pill SWD header |
|---|---|
| SWDIO | DIO (PA13) |
| SWCLK | CLK (PA14) |
| GND | GND |
| 3.3V | 3.3V (power the board from ST-Link, **not** USB at the same time) |

Never connect both ST-Link 3.3V and USB power simultaneously.

### USART1 → CH340

| Blue Pill | USB-UART adapter |
|---|---|
| PA9 (USART1_TX) | RXD |
| PA10 (USART1_RX) | TXD |
| GND | GND |

Cross TX→RX. The on-board CH340 already routes this way if you use the
on-board "USB TO SERIAL" header.

## Software prerequisites (host)

- `arm-none-eabi-gcc` + `make` (xPack 13.3.1 layout supported via `%USERPROFILE%/tools`)
- **OpenOCD** with ST-Link support — required for flash / chip-id / fault dump.
  Without it, flash and debugger stages report `UNAVAILABLE` (Hardware Not Tested) and nothing pretends otherwise.
- `st-info` (stlink tools) for probe discovery — optional but recommended.
- Python 3.11+ with `pyserial`.

## Expected evidence per peripheral (minimum bars)

| Task | Minimum evidence to claim PASS | Status without the fixture |
|---|---|---|
| LED | GPIO probe / debugger register sample of GPIOC_ODR toggle, or user confirmation | compile-only → hardware `UNVERIFIED` |
| USART | Serial line containing literal `CEA:USART:PASS` captured from COM port | `UNKNOWN` |
| USART IRQ/DMA | Same token, generated by the IRQ/DMA path | `UNKNOWN` |
| ADC | `CEA:ADC:value=N` with N in 0–4095, varying with the potentiometer | `PARTIAL` at best |
| PWM | TIM2_CNT incrementing and CCR1 matches configured duty (debugger read), or logic analyzer | `PARTIAL` |
| EXTI | Button press produces the expected IRQ side effect (serial token or GPIO change) | `UNKNOWN` |
| I2C | Address ACK from the EEPROM/SSD1306 in SR1 register read | `UNKNOWN` |
| SPI | Loopback: MISO bytes equal MOSI bytes in a captured transaction | `UNKNOWN` |

## Running

```bash
# discovery (registers devices honestly: CH340 → usb-serial; ST-Link only when present)
POST /api/hardware/discovery

# full pipeline: build → flash → reset → serial → validate
POST /api/hardware/run            {"projectId": "...", "serialDevice": "COM7", "expect": "CEA:USART:PASS"}

# live debugger diagnosis when serial is silent
POST /api/hardware/debugger/diagnose {"projectId": "...", "serialDevice": "COM7"}
```

Every executed pipeline persists a `hardware-runs/hw-*.json` record with
firmware/ELF sha256, git commit, flash output, serial log and evidence —
replayable and auditable.
